# 车载语音已经出字，什么时候才算用户确认了意图？

AI 产品经理精选 · 2026-11-19 · 语音交互与意图确认

**识别出了文字，不代表听完了；一段话听完了，也不代表可以执行。**

想象司机说：“导航去虹桥站……改去虹桥机场 T2。”第一段文字已经清楚，语音识别甚至可能把它封为一个完成片段。如果产品此时就切换路线，它执行的是一段正确的转录，却是错误的最终意图。这里讨论的是导航类任务的交互设计，不是 Moonshine 的现成车机方案。

## 为什么看 Moonshine

[Moonshine](https://github.com/moonshine-ai/moonshine) 是端侧语音工具项目。2026-11-19 核查时，GitHub 首页显示约 **11.5k Stars**（页面舍入值）；选题看的是老项目的近期正式版本 [v0.1.6，2026-11-06](https://github.com/moonshine-ai/moonshine/releases/tag/v0.1.6)，不是把它称为新项目。

[该版本转录文档](https://github.com/moonshine-ai/moonshine/blob/v0.1.6/docs/using/transcription.md) 区分临时文本更新和片段完成：更新事件不保证出现；自然停顿或停止转录时，活动片段都可能收到 `LineCompleted`。这是转录层事件，不是用户给产品的确认。[版本日志](https://github.com/moonshine-ai/moonshine/blob/v0.1.6/CHANGELOGS.md) 还记录了流式回复中断：v0.1.5 增加取消状态，v0.1.6 修复取消旧回复误结束下一条回复。这是回复层事件，也不能当成业务撤回成功。

## 三段产品判断

| 阶段 | 给用户什么反馈 | 系统可以做什么 |
| --- | --- | --- |
| 聆听、暂态识别 | 有文字就标为“识别中”并可更新；没收到临时更新就保留聆听态 | 不根据暂态文字触发导航，不显示已找到唯一目的地 |
| 收到完成片段 | 可以显示稳定文字；候选不唯一时问一句“是火车站，还是机场 T2？” | 保留跨片段修正或否定的机会；不要把识别状态用成执行条件 |
| 意图明确、满足本场景确认要求 | 回显最终目标；收到业务回执后才显示“已开始导航” | 只提交当前版本目标一次。若没有回执，先查实际状态，不把未知说成成功 |

不应该每次都问“确定吗”。对于目标唯一、命令明确且能低成本修改的路线，可以短等待后直接执行；对于停顿后仍在改口、地点歧义，或会覆盖现有路线的情况，优先澄清或确认。等待多久是取舍：太短会误执行，太长会让用户重复下命令。别给所有语种、路况用一个未经验证的阈值。

## 练习：用两套策略走查同一批中文录音

只用合成录音、模拟屏幕与导航接口，不接真车。对照 A「片段完成即执行」与 B「同一轮合并修正、必要时澄清」。两组用同一批音频，覆盖不同停顿长度和噪声。为每轮记录转录片段、目标候选、意图确认时间、执行调用与模拟导航状态。

| 输入或故障注入 | B 组验收预期 |
| --- | --- |
| “导航去虹桥站……改去虹桥机场 T2” | 只提交机场 T2 一次；不能先切到火车站再纠正 |
| “导航去机场……先不用了” | 未提交情形下调用数为 0，当前路线不变；不能把最后一句当闲聊 |
| “导航去虹桥” | 多个合理候选时先澄清。在回答“机场 T2”前不提交 |
| “导航去虹桥机场 T2” | 清楚、完整的正常命令仍能完成，不能靠全部拒绝避免错误 |
| 用户停止此轮后晚到 `LineCompleted` | 不重启这轮意图或提交动作；若动作此前已发出，回读状态后再说明结果 |

建议每类 10 条初步走查，B 组门槛示例：修正及否定样例 **0 次错误导航**，正常样例至少 **9/10 正确完成**；另外报告不必要补问率、首个可见反馈 P95 和实际提交时间 P95，对照 A 看等待成本。样本太小，只能找问题，不能据此声称量产达标。
